## 提供された原文

ゴールデンパス（Golden Path）を実現するために利用されるIaCやCIテンプレートの具体例について、出典に基づき、開発者が「手間をかけずに安全な状態」を維持できる具体的な構成例を整理します。

---

### 1. IaCテンプレート・モジュールの具体例（Secure by Default）

プラットフォームチームが提供する、セキュリティ設定が最初から組み込まれた再利用可能なコンポーネントです。

* **セキュアなインフラの「型」の提供**
  * **暗号化済みCompute Engine (GCP):** 全てのディスクがデフォルトで暗号化されるように設計されたTerraformモジュール。開発者はモジュールを呼び出すだけで暗号化要件を満たせます。
  * **堅牢化済みEC2 (AWS):** KMSキーによるボリューム暗号化と、管理用のSSM権限が最初から付与されたインスタンスプロファイルを含むモジュール。
  * **暗号化済みAzure Instance:** Azure Key Vaultのキーを用いたディスク暗号化が強制されるモジュール。
* **ガードレール付きベースイメージ**
  * **CIS Hardened Images:** OSレベルで脆弱性対策が施され、業界標準のセキュリティベンチマークに準拠した標準イメージを提供し、開発者が自前でベースイメージを作るリスクを排除します。
* **IaCの自動モジュール化**
  * **Terraform Module化:** 暗号化やネットワーク分離、パブリックIPの禁止などの設定をカプセル化し、GitやGCS/S3バケット経由で開発チームに配布します。

---

### 2. CI/CDパイプラインテンプレートの具体例（Automated Quality Gate）

開発者が定義ファイルに数行追加するだけで、高度なセキュリティチェックが実行されるテンプレート（Reusable Workflowsなど）です。

* **標準的なセキュリティ・スキャン・ジョブ**
  * **脆弱性スキャン (SCA/DAST):** Trivyやnpm auditを組み込み、コンテナイメージやライブラリの脆弱性を自動検知するジョブ。
  * **IaC設定ミス・スキャン:** Checkovやcfn-nagをテンプレートに組み込み、TerraformやCloudFormationの設定不備（例：S3の公開設定）をマージ前にブロックします。
  * **秘密情報検査:** TruffleHogやgit-secret、GitHub Secret Scanningを用いて、ソースコード内にAPIキーなどが混入していないかを確認します。
* **サプライチェーン・完全性担保の自動化**
  * **SBOM・来歴(Provenance)生成:** ビルドプロセス中にsyftやslsa-github-generatorを用いてSBOMやSLSA Provenanceを自動生成し、成果物の透明性を確保します。
  * **アーティファクト署名:** 生成されたバイナリやイメージに対し、Cosignを用いてKMS上の鍵で自動署名を行うステップを組み込みます。
* **認証・認可の標準化**
  * **OIDCによる短寿命トークンの利用:** 長期有効なAWS/GCPアクセスキーをシークレットに保存させず、GitHub Actionsの `id-token: write` 権限を利用して、一時的なアクセストークンを取得する設定をテンプレート化します。

---

### 3. Policy as Code (PaC) によるデプロイ制限の具体例

テンプレートから逸脱した設定がデプロイされるのを防ぐ「検問」としての実装です。

* **デプロイ前の検証**
  * **OPA (Open Policy Agent):** Tfplan（Terraformの実行計画）をJSON形式で抽出し、Conftestを用いて「特定のインスタンスタイプ以外は許可しない」「IAMの権限が広すぎる」などのルールを自動検証します。
  * **HashiCorp Sentinel:** Terraform Cloudにおいて、企業ポリシーに反するインフラ変更をハード失敗（デプロイ停止）させるルールセット。

---

> これらの具体例を組み合わせることで、「プラットフォームチームが安全な部品（IaCモジュール）と、それを検証する自動ライン（CIテンプレート）を提供し、開発者はそれを利用するだけで迅速かつ安全にリリースできる」というゴールデンパスが実現されます。

IaC（Infrastructure as Code）モジュールの標準化とPolicy as Code（PaC）の具体的な連携は、「安全な標準（ゴールデンパス）」をテンプレートとして提供し、その遵守を「自動化された関所（ガードレール）」で強制するという構造で実現されます。

出典に基づき、具体的な連携手法を4つの主要なアプローチに整理して解説します。

---

### 1. CI/CDパイプラインにおける「品質ゲート」としての連携

最も一般的で強力な連携方法は、CI/CDパイプライン内にPaCを**「決定ゲート（Decision Gate）」**として組み込むことです。

1. **標準モジュールの配布:** プラットフォームチームが、暗号化やネットワーク制限がデフォルトで設定されたTerraform等の標準モジュールをプライベートレジストリやリポジトリ経由で提供します。
2. **マージ前の自動検証:** 開発者がこれらのモジュールを呼び出すコードをコミットすると、CIパイプライン上でPaCツール（Checkov, OPA, Sentinelなど）が起動します。
3. **デプロイの拒否:** もし開発者が標準設定を上書きして脆弱な設定（例：パブリックIPの付与）を行った場合、PaCツールがそれを検知し、パイプラインを「失敗」させてデプロイを自動的にブロックします。

---

### 2. インフラ定義（tfplan等）の構造的検証

PaCツールは、標準化されたモジュールが生成する「実行計画」を解析することで、ポリシーとの整合性を検証します。

* **Terraform Planの解析:** `terraform plan` の出力をJSON形式に変換し、それをOPA（Open Policy Agent）やSentinelで読み込みます。
* **パラメータの強制:** 「特定のモジュールを使用する際は、必ずこのタグを付与する」「特定のリージョン以外でのリソース作成を禁止する」といった、組織の標準（Standard）に沿ったルールをコード（RegoやSentinel言語）で定義し、実行計画に対して適用します。
* **モックデータによるテスト:** 開発段階では、標準モジュールが生成するデータを「モック」として使用し、事前にポリシーが正しく動作するかをテストできます。

---

### 3. クラウドネイティブな「フック（Hooks）」による強制

CI/CDをバイパスした変更に対しても、インフラのプロビジョニング段階で標準を強制する仕組みです。

* **IaC Hooksの活用:** 例えばAWS CloudFormation Hooksなどを使用し、リソースが作成・更新される直前に、その内容が組織のポリシーに適合しているかを検証します。
* **中央集約型ポリシーエンジン:** 独自の検証ロジックを何個も作るのではなく、Hookから中央のOPAサーバーを呼び出すことで、IaCの記述内容が標準化されたパターンから逸脱していないかを一元的に判定できます。

---

### 4. 継続的なドリフト検知と自動修正

デプロイ後も、標準化された状態から変化（ドリフト）していないかを監視し続けます。

* **構成準拠の監視:** Cloud Custodian（c7n）などのPaCツールを使用して、本番環境のリソースがIaCで定義された標準状態を維持しているかを定期的にスキャンします。
* **自動修復（Corrective Control）:** 標準から外れた設定（例：公開されたS3バケット）を検知した場合、自動的にタグを付与して警告したり、設定を標準状態に強制的に戻したりするアクションを実行します。

---

### 連携を支える「Security as Code」のフロー

この連携を実効的なものにするためには、以下のフローを回すことが推奨されます。

1. **要求定義:** ASVSなどの標準に基づきセキュリティ要求を定義。
2. **テンプレート化:** 要求を満たすIaCモジュールを「ゴールデンパス」として作成。
3. **ポリシー化:** そのモジュールの使い方をPaCのルールに落とし込む。
4. **検証:** パイプラインやランタイムで継続的に検証。

---

> このように、**標準モジュール（正解の型）とPaC（型チェックの自動化）**を組み合わせることで、開発速度を落とさずに「Security by Default」を実現することが可能になります。
